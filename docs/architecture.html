Architecture

RepoAtlas is a small monorepo: a Next.js frontend, a FastAPI service that owns all analysis and tour logic, and managed Postgres + Auth from Supabase. It is designed to run entirely on free tiers — one web service, one database — without giving up a durable job queue.

Authentication

The frontend uses @supabase/ssr with GitHub as the OAuth provider. After the PKCE redirect, /auth/callback exchanges the code for a session cookie. Every API call then carries Authorization: Bearer <Supabase access token>.

The API (core/security.py) reads the token's alg header and verifies it with:

  • RS256 / ES256 — the project's JWKS at {SUPABASE_URL}/auth/v1/.well-known/jwks.json, fetched off the event loop and cached for 10 minutes; or
  • HS256 — the legacy SUPABASE_JWT_SECRET, for projects that still use shared-secret signing.

aud (default authenticated), exp and sub are required, with 10 s leeway. The JWT sub becomes the user id stored in *_user_id columns, and the GitHub username comes from user_metadata.user_name. Tokens are never logged. Routes declare either AuthUser (401 without a valid token) or OptionalUser (anonymous allowed, but an invalid token is still a 401). Authorization lives in the services: non-owners get FORBIDDEN, other users' private tours are NOT_FOUND.

GitHub integration

Every analysis touches GitHub a fixed number of times, independent of repository size (services/github_service.py):

  1. Resolve the ref — GET /repos/{owner}/{repo} (default branch, description, stars; private repositories are rejected) and GET /repos/{owner}/{repo}/commits/{ref} to pin the exact commit SHA.
  2. Download the snapshot — GET /repos/{owner}/{repo}/tarball/{sha}, following the redirect to codeload, streamed and aborted above MAX_TARBALL_BYTES (80 MB). The archive is extracted in memory: only regular files, no symlinks/hardlinks, absolute or .. paths rejected, vendor/build directories skipped, files over MAX_FILE_BYTES and non-UTF-8/binary files skipped.

Rate-limit headers are recorded on every response and exposed at GET /api/v1/github/rate-limit. Errors map to stable codes: 404/451 → GITHUB_REPO_NOT_FOUND, 403/429 with an exhausted quota → GITHUB_RATE_LIMITED (with details.reset_at), 5xx and timeouts → GITHUB_UNAVAILABLE after three attempts with exponential back-off (0.5 s, 1 s).

Embedded DB-backed worker

There is no Redis or separate queue service. The analyses table is the queue (workers/analysis_worker.py):

  • Heartbeat & stale-lock recovery. Each status transition stamps locked_at. A job whose lock is older than WORKER_STALE_LOCK_SECONDS (600 s) belongs to a dead worker and is reclaimed by the next poll.
  • Attempt cap. attempts is incremented on every claim; a job claimed a fourth time is marked FAILED with “Gave up after 3 attempts” instead of crashing the worker forever.
  • Graceful shutdown. On shutdown the running job is allowed to finish (30 s grace) before the task is cancelled.
  • Inline runs. Sync & verify needs a completed analysis of the newest commit immediately, so it claims the row itself (fresh lock) and runs the pipeline inline, or waits up to 120 s if a live worker already owns it.
  • Modes. WORKER_MODE=embedded (default) starts the loop in the API's lifespan; standalone expects python -m app.workers.analysis_worker as a separate process; off disables it (tests).

Data model

Eight tables, defined in db/models.py and created by Alembic migrations. User identity is not stored in a users table: *_user_id columns hold the Supabase JWT sub.

  • One analysis per commit. UNIQUE (repository_id, commit_sha) is what makes re-analysis of an unchanged commit free and race-safe (INSERT … ON CONFLICT DO NOTHING).
  • File contents live with the analysis. file_nodes.content is the exact source at the pinned commit (deferred-loaded), so the code viewer, tour pinning and drift detection never call GitHub again.
  • Steps keep their own snapshot. snippet_snapshot + snippet_hash are what drift detection compares against; proposed_* and drift_diff hold the latest review proposal.
  • Sync history. Each Sync & verify appends a tour_sync_runs row with the from/to commits and per-status counts; the dashboard shows the last 10.

Request lifecycle

  • Request ids. A valid incoming X-Request-ID ([A-Za-z0-9._:-]{1,128}) is propagated, otherwise a UUID is generated. It is echoed on the response (and exposed via CORS), attached to every log record and included in details.request_id of unexpected 500s.
  • Structured logs. In production (ENVIRONMENT=production) logs are single-line JSON on stderr; in development they are readable text. One access line per request with method, path, status and duration.
  • Error envelope. Routes stay thin and return ok(data); services raise AppError(ErrorCode.X, message, details=…). Validation errors return only loc/msg/type (input is never echoed); stack traces are logged, never returned. See the error code table.

Key decisions & trade-offs

DecisionWhyTrade-off
Contract-first OpenAPIapp/schemas/atlas.py is the contract. npm run gen:api dumps the OpenAPI document to frontend/openapi.json and generates src/lib/api/schema.d.ts; the frontend never hand-writes API types. CI fails if the committed document differs from the generated one.Any schema change requires regenerating and committing the types.
One tarball instead of per-file fetchesA fixed, small number of GitHub requests per analysis regardless of size keeps anonymous use inside the 60 req/h limit.The whole archive is downloaded even if only some files are analyzed; capped at 80 MB.
Commit SHA pinningEvery analysis, file content and tour anchor refers to one immutable commit, so results are reproducible, deduplicated per commit and safely cacheable.Viewing “latest” requires a new analysis (or a tour sync).
Deterministic, iterative algorithmsNo recursion (real repositories exceed Python's stack), sorted outputs everywhere: identical input gives identical graphs, cycles and ranks; everything is unit-testable.Slightly more verbose code (explicit stacks).
Embedded workerOne free web service + one free Postgres run the whole product; SKIP LOCKED + heartbeats give durability without Redis.Analysis competes with requests for the same CPU; concurrency is 1 per process. WORKER_MODE=standalone splits it out.
tree-sitter >=0.25,<0.260.26.0 segfaults when walking named_children after field lookups on trees with MISSING nodes — a native crash that would take down the worker.Pinned until fixed upstream.
LRU graph cacheCompleted analyses are immutable, so the in-memory graph is cached (32 entries) per analysis id; blast-radius queries cost one BFS, not a DB round trip.Per-process memory; invalidated when an analysis is forced to re-run.
Checkpoint answers never leave the serverTrainees receive only question and options; correct_index/explanation are projected out in one serializer. The explanation is returned only after a correct answer.Owners and trainees see different step payloads.
Transaction poolerSupabase's pgbouncer pooler (port 6543) survives many short-lived connections from a sleeping free instance.Prepared statements are disabled (statement_cache_size=0).
