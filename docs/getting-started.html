Getting started

This walkthrough follows the hosted app from pasting a repository URL to reading a tour's health report. The figures are illustrations of the real screen layouts; where screenshots have been added they replace the illustrations automatically.

Open the app Run it locally instead

The hosted app URL hasn't been published in this documentation yet — see Self-hosting to run your own instance.

Before you start

  • Public repositories only. Private repositories are rejected with GITHUB_REPO_NOT_FOUND; RepoAtlas never asks for repository access.
  • Python, JavaScript and TypeScript files are analyzed (.py, .js, .jsx, .mjs, .cjs, .ts, .tsx, .mts, .cts).
  • No account needed to explore. Analyzing repositories, browsing graphs, blast radius and reading public tours work anonymously. Creating tours, tracking progress and the dashboard require signing in with GitHub (Supabase Auth).

1 · Analyze a repository

  1. On the home page paste a repository as https://github.com/owner/repo, github.com/owner/repo/tree/branch or simply owner/repo, then press Analyze. Or click one of the demo repositories.
  2. Optionally open Choose a branch; leave it empty to use the repository's default branch.
  3. RepoAtlas resolves the branch to a commit SHA and queues an analysis. If that exact commit was analyzed before, you are taken straight to the cached result.

2 · Follow the analysis progress

The analysis page polls the job and shows a five-step progress indicator that mirrors the server-side state machine: Queued → Fetching tree → Parsing ASTs → Computing graph → Ready.

When a job fails the step it failed in turns red and a specific explanation is shown — for example GitHub rate limit reached (retry later or sign in), Repository not found (private or misspelled), Repository too large or No supported source files. See Troubleshooting for causes and fixes.

Large repositories

At most MAX_FILES source files (1,500 by default) are analyzed. Files under src/, app/, lib/ and packages/*/src/ are preferred, then shallower paths. A truncated badge tells you when the cap was hit.

3 · Read the dependency graph

When the analysis completes, the summary stats and the graph workspace appear. Each node is a file; an arrow A → B means A imports B. Nodes are coloured by role and laid out automatically (left-to-right by default).

Toolbar and filters

  • Search (/) jumps to a file, or applies a path contains filter.
  • Cycles isolates files and imports that are part of a circular dependency (disabled when there are none).
  • Hide tests hides test files and fixtures; Hide isolated hides files with no project imports in either direction.
  • Role and language chips filter by classification; counts are shown on each chip. Clear filters resets everything.
  • The LR / TB button switches the layout direction; the panel button collapses the inspector on desktop.
  • The statistics show visible / total Files and Imports and the number of reported Cycles (shown as 100+ when the report cap is reached).

Overview panel

With nothing selected, the right-hand panel lists the most central files by PageRank (great first files to read), the repository's entry points (files nothing imports) and a count per role. The Legend in the top-left corner of the canvas explains role colours, edge styles (solid = static import, dashed = dynamic or type-only, red = circular) and, once a file is selected, blast-radius depth colours.

Shareable links

Selecting a file writes it to the URL as ?file=path/to/file.py, so you can send a colleague a link that opens the graph focused on that file.

4 · Simulate the blast radius of a change

Click any node (or press Enter on a focused node). The inspector opens on the Impact tab and the graph is recoloured by distance from the selected file.

  • Risk score = Σ (1 / depth) over impacted files ÷ (total files − 1) × 100, bucketed as Low < 5 Medium < 15 High < 35 Critical ≥ 35. The panel's “How is the risk score computed?” disclosure explains it in place; the algorithms page animates it.
  • Impacted is the number of files that import the selected file directly or transitively, with the percentage of all other files; Direct counts depth-1 importers; Max depth is the longest import chain.
  • Click any dependent to jump to it. Hide on graph turns the depth colouring off without closing the inspector.
  • The Code tab shows the file's source at the analyzed commit with an Open on GitHub permalink. The Details tab shows in/out-degree, PageRank and rank, lines of code, language, circular membership (with its SCC group), exports, functions, classes, each import with its line number and kind, and any parse warning.

Press Esc to clear the selection. On small screens the inspector opens as a sheet from the right.

5 · Find circular dependencies

Toggle Cycles in the toolbar to show only files and imports that lie on a cycle (they are drawn in red), or open List cycles for the concrete cycles.

Cycles come from an iterative three-colour DFS (concrete cycles) combined with Tarjan's strongly connected components (complete membership). See Algorithms → cycle detection.

6 · Create a tour

Tours are created from a repository page (/repos/owner/name) once the repository has a completed analysis. Sign in with GitHub first.

  1. Click Create tour.
  2. Enter a title (3–200 characters) such as “How a request flows through the API”, an optional description (what will trainees learn?) and choose the visibility: Public tours are listed for everyone; Private tours are invisible to anyone but you.
  3. The tour is created against the analysis you are looking at — its commit becomes the tour's base commit — and the tour builder opens.

7 · Pin lines of code

The builder has three panes: the ordered step list, the dependency graph (files already used by steps are highlighted) and the code / step editor.

  1. Click a node in the graph or use Jump to file to open a file.
  2. Select a range of lines in the code viewer (a step may pin at most 400 lines beyond its first line) and click Pin lines.
  3. Give the step a title and a Markdown explanation, optionally add a checkpoint and choose its position, then save. The server extracts the snippet from the stored file content and records a SHA-256 hash of its whitespace-normalized text — this anchor is what the drift engine checks later.
  4. Reorder steps by drag and drop or with the move up/down buttons; click a step to edit its text or checkpoint; delete steps you no longer need.

8 · Add checkpoints

A checkpoint is a multiple-choice question attached to a step: a question (3–500 characters), 2 to 6 options, exactly one correct option and an optional explanation (up to 1,000 characters).

  • Trainees never receive correct_index or the explanation — the API only sends them to the tour owner. The explanation is revealed after a correct answer.
  • Steps without a checkpoint are completed with Mark as done.
  • The first attempt at each checkpoint is recorded, which powers first-try accuracy on the owner's dashboard.

9 · Play a tour

Open a tour's public page (/tours/<id>) to take it. Anyone can read a public tour; signing in lets RepoAtlas track your progress.

Steps must be completed in order: the server rejects an answer with CONFLICT (“Complete the previous steps first”) if any earlier step is incomplete, so the Next button only unlocks once the current step is done. A wrong answer can be retried; finishing the last step shows a completion screen.

10 · Sync & verify drift

Code changes after a tour is written. In the builder, click Sync & verify. RepoAtlas resolves the newest commit on the tour's branch, makes sure it is analyzed (reusing the cached analysis when nothing changed), re-evaluates every step and shows a sync report with each step's previous and new status.

StatusMeaningWhat happens
HealthyThe pinned lines are unchanged.Nothing to do.
Auto-fixedThe same code moved to other lines.Line numbers are updated automatically.
Needs reviewThe pinned code itself changed.A proposed location, similarity score and diff are stored for you to review.
File deletedThe file no longer exists in the new snapshot.Re-pin the step to another file or delete it.
UnverifiedNot yet checked against a newer commit.Run Sync & verify.

Open a step that needs attention to review it:

  • Accept proposed location re-pins the step to the proposed lines (available when a confident match was found).
  • Keep original lines re-pins the same line numbers against the new code.
  • Re-pin manually lets you select a new range in the same file.
  • For a deleted file, Re-pin to another file picks a new file and range; title, explanation and checkpoint are kept.

Each resolution recomputes the snippet and hash, and marks the step Healthy. Every sync is stored, so the dashboard can show the tour's sync history. The details of the matcher are on the algorithms page.

11 · Use the dashboard

The signed-in dashboard (/dashboard) has three tabs:

  • Repositories — up to 10 repositories you analyzed or own tours for, each with its latest completed analysis: file, import and cycle counts, god modules, entry points, role and language breakdowns and the five riskiest files by blast-radius risk score.
  • Tour health — every tour you own with its health score (share of steps that are Healthy or Auto-fixed), drift counts, the last 10 sync runs and per-trainee progress: completed steps, first-try accuracy and last activity.
  • My learning — public tours by other people that you are taking, with your completion percentage.
