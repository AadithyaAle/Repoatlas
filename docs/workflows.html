Concepts

Workflows

Everything RepoAtlas does is one of four end-to-end workflows. This page follows each one through the API and the database, with the exact states, error codes and rules enforced by the server.

1 · Ingestion: analyze a repository

POST /api/v1/repos/analyze with {"repo_url": "owner/repo", "branch": null, "force": false}. Accepted URL forms include https://github.com/owner/repo, github.com/owner/repo/tree/branch and owner/repo; anything else is INVALID_REPO_URL.

Enqueue & dedupe per commit

  1. Resolve the ref synchronously. Repository metadata + the branch's current commit SHA come from GitHub inside the request, so “not found”, “private”, “empty repository” and “branch not found” fail fast with an HTTP error instead of a queued job.
  2. Upsert the repository (owner/name are unique) with the latest description, stars and default branch.
  3. Insert-or-reuse the analysis. INSERT … ON CONFLICT (repository_id, commit_sha) DO NOTHING, then lock the row. A COMPLETED or in-flight analysis of the same commit is returned as-is — so analyzing an unchanged repo is instant. A FAILED one is reset to PENDING; force: true also resets a completed one (never an in-flight one, which a worker owns).
  4. Respond 202 Accepted with the AnalysisOut. The frontend polls GET /api/v1/analyses/{id} until a terminal status.

State machine

StatusWhat happens
PENDINGWaiting in the analyses queue for a worker (claim loop).
FETCHING_TREEDownloads /tarball/{sha}, extracts supported sources and tsconfig*.json/jsconfig.json in memory and applies the file cap.
PARSING_ASTIn a worker thread: parse every file (Python ast; tree-sitter for JS/TS), resolve imports into edges, build the graph, detect cycles, compute degrees, roles and PageRank. A file that fails to parse gets a parse_warning and never aborts the analysis.
COMPUTING_GRAPHPersists file_nodes (with content) and edges in chunks of 1,000 rows and the summary counters (files, edges, cycles, warnings, unresolved/external imports, language breakdown, up to 100 cycles).
COMPLETEDGraph, files and blast radius are queryable. Before this, GET …/graph returns 409 ANALYSIS_NOT_READY.
FAILEDerror_code/error_message are stored on the row; unexpected exceptions are logged and stored as INTERNAL_ERROR with a generic message.

Errors raised while resolving the ref are returned directly by POST /repos/analyze; errors raised inside the worker are stored on the analysis and surfaced by the progress page.

Filtering, prioritisation & truncation

  • Skipped directories: node_modules, .git, dist, build, .next, out, coverage, __pycache__, .venv, venv, vendor, site-packages, .tox, .mypy_cache.
  • Skipped files: minified bundles (*.min.js, *.min.mjs, *.min.cjs), declaration files (*.d.ts, *.d.mts, *.d.cts), files larger than MAX_FILE_BYTES (300 kB), non-UTF-8 or binary files.
  • Priority order when there are more than MAX_FILES (default 1,500) candidates: files under a top-level src/, app/ or lib/, or under packages/*/src/, come first; then shallower paths; then alphabetical. The first MAX_FILES are analyzed.
  • Reporting: total_source_files is the count before the cap, analyzed_files after it, and truncated is true when the cap was hit (the UI shows a “truncated” badge). Imports into files that were cut off cannot become edges (they are usually counted as unresolved).

2 · Blast radius & cycles

Both features are pure graph algorithms over the immutable graph of a completed analysis. Cycles are computed once during ingestion; blast radius is computed on demand.

  • Reverse BFS walks importers of the selected file level by level; every impacted file gets its depth (1 = imports it directly).
  • Impact = impacted ÷ (N − 1) × 100. Risk = Σ (1 / depth) ÷ (N − 1) × 100, bucketed Low < 5 Medium < 15 High < 35 Critical ≥ 35. Step through it on the algorithms page.
  • Cycles come from an iterative three-colour DFS (concrete cycles, canonicalised so the smallest path comes first, at most 100) and Tarjan's SCC, which marks every file (is_circular, scc_id) and import (is_circular) on any cycle. They are returned with the graph by GET /analyses/{id}/graph. See cycle detection.
  • The dashboard reuses the same function to list each repository's five riskiest files.

3 · Pin-to-code tours

Pinning a step

POST /api/v1/tours/{tour_id}/steps with file_path, start_line, end_line, title, optional body_markdown, checkpoint and position. The client never sends code: the server reads the file from the tour's analysis snapshot, slices the 1-based inclusive range and stores

  • snippet_snapshot — the raw lines exactly as pinned;
  • snippet_hash — SHA-256 of the lines after normalisation (each line stripped, internal whitespace runs collapsed to one space, blank lines kept, joined with \n). Re-indenting code therefore does not change the hash.

The new step starts Healthy. A path that is not in the snapshot is FILE_NOT_IN_SNAPSHOT; a range outside the file is INVALID_LINE_RANGE (with details.loc). Steps can be edited (title, Markdown, checkpoint, remove_checkpoint), reordered with PUT …/steps/order (every step id exactly once) or deleted (positions are compacted).

Checkpoints & ordered completion

  • POST …/steps/{step_id}/answer with selected_index (or null to acknowledge a step without a checkpoint). An index outside the options is VALIDATION_ERROR.
  • If any earlier step (by position) is not completed by this user the answer is rejected with 409 CONFLICT — “Complete the previous steps first”.
  • Each answer increments attempts; first_try_correct is recorded on the first attempt of a step with a checkpoint; a correct answer marks the step completed. The explanation is returned only when the answer is correct.
  • GET …/progress returns completed step ids and percent_complete; the owner's dashboard aggregates completed steps, first-try accuracy and last activity per trainee.

4 · Drift engine: Sync & verify

POST /api/v1/tours/{tour_id}/sync (owner only) re-checks every step against the newest commit of the tour's branch.

  1. Resolve the latest commit of the branch the tour's analysis was made on.
  2. Ensure it is analyzed. If that commit already has a completed analysis it is reused (an unchanged branch costs no pipeline run); otherwise the pipeline runs inline in the request, or waits up to 120 s for a worker that already owns the job. A failed analysis surfaces its stored error.
  3. Evaluate every step with the decision tree below against the file contents of the new snapshot.
  4. Apply results: auto-fixed steps get their new line numbers (and snapshot) immediately; review steps get proposed_start_line/proposed_end_line, proposed_snippet, drift_similarity and a unified drift_diff; every step records last_checked_at/last_checked_commit_sha.
  5. Move the tour forward (analysis_id, base_commit_sha, last_synced_at) and append a tour_sync_runs row with the from/to commits and per-status counts.
  6. Return the sync report: per-step previous/new status and line ranges, counts, and up_to_date when nothing changed.

Decision tree

Status legend: Healthy Auto-fixed Needs review File deleted Unverified (the column default; steps created through the API start Healthy).

Resolve actions

POST /api/v1/tours/{tour_id}/steps/{step_id}/resolve with an action. Every successful resolution re-extracts the snippet from the tour's (new) snapshot, recomputes the hash, clears the proposal and marks the step Healthy.

ActionEffectAllowed when
accept_proposedRe-pin to proposed_start_line–proposed_end_line.Step is Needs review / File deleted and a proposal exists; otherwise 409 CONFLICT.
keep_originalRe-pin the same line numbers against the new code.Step is Needs review / File deleted and the file still exists; otherwise 409 CONFLICT.
repinRe-pin to the given start_line/end_line (both required) in the same file.Any status. Out-of-range lines are INVALID_LINE_RANGE.

For a deleted file, the builder's Re-pin to another file creates a new step at the same position in the chosen file (keeping title, explanation and checkpoint) and deletes the old one.

Sync runs history

Each sync stores a tour_sync_runs row: who triggered it, from_commit_sha → to_commit_sha and a count per drift status. The dashboard's Tour health tab shows the last 10 runs per tour together with the health score — the share of steps that are Healthy or Auto-fixed.
